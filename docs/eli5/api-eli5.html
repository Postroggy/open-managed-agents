🚪 internal/api 是干嘛的？

它是整个后端的「总大门 + 接线总站」

🏢
所有请求进来，都先经过它 —— 再分门别类送进各个业务小屋
它自己不干活，但知道谁来敲门、该送进哪个房间、进门要先过哪些检查
就像一个物业总台，负责把客人带到正确的房间 🗺️
🚦 总台怎么分流？（看 server.go 真实代码）
🔑

带 API Key 的客人

/v1/*

走「服务通道」→ 各资源小屋
（agents/sessions/files…）

🎟️

带平台会话的客人

/v1/*（平台通道）

走「平台通道」→ 同样的资源小屋
（平台身份鉴权）

🖥️

控制台客人

/api · /auth · /oauth

走「平台控制台」→ 登录/注册/组织管理/工作台

💡 看完代码的 Insight
🏗️ 它只「组装」，不「干活」

server.go 里没有业务逻辑 —— 只有 NewHandler、Mount、Use。真正的活儿全在 resource 包（agents/sessions/...）里。

🔀 一个 /v1 两条通道

同一套资源路由（mountSharedV1Resources）被 service 和 platform 两条鉴权通道复用 —— 一套代码，两种身份。

🩺 健康检查在最前面

GET /healthz 不挂任何中间件 —— 负载均衡探活时不能要求带 key。

🧩 依赖注入集中地

db、objectStore、logger、skillPrewarmEnqueuer 全在这里组装好，再分发给各资源包 —— 这是"组装层"的定义。
