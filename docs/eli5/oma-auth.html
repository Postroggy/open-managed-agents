🏢 前台接待处 & 查票的保安

每一个请求走进大楼，都要过两道关：
前台（server.go）告诉它往哪走 · 保安（auth）决定放不放行

第 1 章

整栋大楼，只有 一 个大门

不管什么请求 —— SDK 调来的、浏览器点来的、登录用的 —— 都从 同一个门 进来。

🚪 大门 = internal/api/server.go
你写的 Server 只有一个方法：ServeHTTP(w, r) —— 全部请求都从这里进
▼
🎛️ 前台大厅（chi router）
先是 3 个通用中间件（所有人都过），再按 URL 前缀 分流 到 3 个区域
▼
🧾 request-id 中间件 → 📋 requestLogging → 🛡️ recover
先给每个请求发一张编号纸条（没有就用 req_xxx 现场生成）→ 记账 → 万一里面程序崩溃（panic），保安兜住，客人只看到"内部错误"，不会看到堆栈
第 2 章

进了大厅，分流到 3 条走廊

前台只看 URL 开头，把请求扔给三条不同的走廊。

🎟️ 分流规则（server.go 第 113~124 行）
A
/v1 → 安thropic 兼容入口（双通道路由器）
这是给 SDK 和代码 用的门。它自己不鉴权，而是先看请求身上带的是 哪种门票，再决定走哪条内线（见第 4 章）。
B
/api /auth /oauth /web-api → 控制台走廊
这是给 浏览器网页 用的门：登录、注册、组织管理、MCP 目录、工作台，全部挂在这里。
C
/healthz → 健康检查（不用门票）
运维探活的，直接回 {"status":"ok"}。
💡 为什么只在大门口拦？ 因为里面是一棵 chi 路由树：/v1 走廊里又挂满了 /agents、/files、/sessions、/webhooks …… 每个资源是一个 handler（第 11 行起的各种 Handler 字段）。 在大门口统一鉴权一次，里面所有部门就都 默认安全，不用每个部门自己再查一遍门票。
第 3 章

三种门票：谁 在敲门？

保安问的第一句话是：你出示的是哪种门票？

API 钥匙 · SDK / 代码
🗝️ sk-ant-xxx
放在请求头 X-Api-Key 或 Authorization: Bearer ...
  • 是 Anthropic 风格 的钥匙，发给"机器"用
  • 只在 /v1 走廊有效（走廊 A 的内部鉴定逻辑）
  • 丢了也不怕：数据库里存的是 哈希，不是原文
平台会话 · 浏览器
🍪 sessionKey Cookie
登录后浏览器自动随身携带
  • 有效期 300 天（DefaultTTL），存在 Redis 或内存
  • 是"人"的凭证：能知道你 是谁（user）
  • 在 /v1 走平台通道，在 /api 走控制台
环境钥匙 · 特殊任务
🔑 env_key
给沙箱环境（environment）跑任务用的
  • 是"兜底"票：只对 /v1/environments/.../work、/v1/sessions、/v1/skills 生效
  • API 钥匙查不到时，才会试这张票（见第 4 章）

没有

这就是 apiEntrypointRouter（第 144 行）：它只看"带没带钥匙"，不做真鉴定，鉴定留给里面的中间件 —— 判断与执行分离。

第 5 章

保安验票三步：不读原文，只对指纹

保安很聪明：他不看钥匙长什么样，只看 指纹 对不对。

STEP 1 · 打指纹
SHA-256
auth.HashAPIKey(key) → 64 位十六进制哈希
➡️
STEP 2 · 对指纹
查数据库
GetAPIKey(keyHash) 一条 SQL 连查 3 张表（见下）
➡️
STEP 3 · 发身份卡
Principal
塞进 context，整条链路都认得它

🔍 一条 SQL 查到"你是谁"（db.go 第 437 行）

SQL 做了什么
api_keys JOIN workspaces JOIN organizations
WHERE key_hash = ? AND status = 'active' AND (expires_at IS NULL OR expires_at > now())

一张表查清 钥匙 → 工作区 → 组织 三层归属；同时把 停用（status）和过期（expires_at） 都挡在门口。没查到 → ErrNotFound → 401。

🧠 为什么存哈希不存原文？ 数据库泄露了，小偷也只拿到指纹，没法反推钥匙。 但指纹是"确定性"的（同一钥匙永远同一指纹），所以数据库不存明文、日志里也别出现明文 —— 这是安全底线。
第 6 章

身份卡 Principal：一卡走全楼

验完票，保安发一张身份卡。之后所有部门都从 context 里掏卡认人，不再问第二遍。

🎫 身份卡 · Principal internal/auth/auth.go
怎么来的

第 7 章

三道闸门：严 → 松 三个等级

不是所有走廊都同样严格。保安有几套不同的闸门。

🔒
闸门 1 · 必须验票（service / platform 通道）
serviceAuthMiddleware / platformAuthMiddleware：验不过 → 401，请求结束。 平台通道还会尝试镜像会话恢复（cookie 失效但能凭数据库身份重建会话），并检查 X-Organization-UUID / X-Workspace-ID 覆盖头 —— 前端切组织/工作区靠它。
🧸
闸门 2 · 可选验票（部分控制台路由）
optionalPlatformAuthMiddleware：有 cookie 就验、验失败就清除，没有/失败也放行 —— 登录页、目录页这种"没登录也能看"的地方用。
🫖
闸门 3 · 不验票（healthz / 登录接口本身）
健康检查和"登录这个动作"当然不能先验票 —— 登录接口本身就是发门票的地方。
错误场景状态码错误类型谁能看到
没带钥匙401authentication_error任何人
钥匙是假的 / 已停用 / 已过期401authentication_error任何人
钥匙真的，但组织/工作区没权限403permission_error只有持真票者能触发
内部错误（数据库挂了等）500api_error任何人（但不泄露细节）

401 = 你是谁？· 403 = 我知道你是谁，但你不许进。· 这是 Anthropic 兼容错误结构（internal/httpapi.WriteError）。

第 8 章

保安的边界：管验票，不管业务

"这扇门你能不能进"由保安管；"进来看哪个柜子"由各部门自己管。

✅
auth 层只做三件事
提取凭证（头 / cookie）→ 哈希比对（HashSecret）→ 产出 Principal。 db 层只做数据查询（GetAPIKey），不含"这个用户能不能删这个文件"这种决策。
🚫
不归保安管
业务授权（谁能删谁的文件）→ 各资源 handler 自己查； 权限决策不得沉到 internal/db —— db 不认识 HTTP，也不认识"用户能不能干这事"。
