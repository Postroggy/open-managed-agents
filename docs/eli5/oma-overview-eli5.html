第三章 · 关键数据流

四股核心数据怎么流动

💬 消息流（用户 ↔ Agent）
用户 POST /events→ managedagentsevents 分类→ sessionfanout 广播→ stream_hub SSE→ codesessions → 沙箱 worker
sessions 是"对外脸面"，codesessions 是"背后发动机"，事件字典裁决每个事件去哪
📁 文件流（沙箱 ↔ 存储）
sandboxmount 路径合同→ filestore（/uploads 固定根）→ storage（S3 blob）→ db（元数据）→ cleanup（孤儿清理）
"内容进 S3、元数据进 DB" 是统一模式；沙箱可死，数据不死
🔑 密钥流（vault → 运行时注入）
用户存 Credential→ vaults.SealCredentialSecret→ secrets.Seal（DEK/KEK 信封）→ DB 存信封→ Agent 调 MCP → vaults.Injector → secrets.Open → 注入 Authorization
secrets = 锁匠（加密工具），vaults = 银行（业务）；明文绝不落库/缓存
🎯 模型流（Claude 兼容 → 真实上游）
用户请求模型名→ modelmapping.Resolve 翻译→ messages 代理转发→ 上游模型（BYOK）
models 目录展示翻译后的模型；platformapi 组织级代理也走 modelmapping
第四章 · 依赖金字塔

谁依赖谁（简化版）

🎡 资源层（agents/sessions/skills/...）
  ↓ 依赖
🎬 运行时层（codesessions/environments/filestore/...）
  ↓ 依赖
🧩 共享合同（sessioncontract/sessionresource/sandboxmount/filestorepath/managedagentsevents）
  ↓ 依赖
🏗️ 基础设施（db/storage/secrets/config/networkpolicy）
  ↓ 依赖
🧰 纯工具（common/collections · common/jsonx · ids）

铁律：依赖只能往下，不能往上（db 不能 import 资源包；工具层不依赖业务层）

💡 多个"合同包"（sessioncontract/sandboxmount/filestorepath）存在的意义：让各层对"路径/上限/语义"的理解一致，防漂移。
第五章 · 理解地图

如何记住这 45 个包

🧠 记忆锚点 1：一条主线 —— "用户让 Agent 干活"：
  登录(平台层) → 建 Agent(agents) → 建环境(environments) → 建会话(sessions) → 发消息 → 沙箱干活(运行时层) → 调工具(凭证) → 通知(webhooks)

🧠 记忆锚点 2：三驾马车 —— 数据去哪：
  元数据 → db（PostgreSQL）· 大内容 → storage（S3）· 会话状态 → redisclient（Redis）

🧠 记忆锚点 3：四个"合同包" —— 共享语义防漂移：
  sessioncontract（上限）· sandboxmount（路径）· filestorepath（路径语义）· managedagentsevents（事件字典）

🧠 记忆锚点 4：三对"易混包"：
  secrets vs vaults（工具 vs 业务）· sessions vs codesessions（对外 vs 发动机）· platform vs platformapi（数据 vs 接口）

🧠 记忆锚点 5：异步三兄弟 —— 入队即返回：
  skillprewarm（技能预热）· cleanup（对象清理）· webhooks（事件投递）—— 全是"队列 + worker"模式
