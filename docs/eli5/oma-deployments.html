OMA 内部参观 · 第 5 站

🚿 Deployments & docker-compose：两套"一键装置"

这页讲 两个"deploy"，一个是产品功能，一个是运维工具：
上集 deployment —— 把 agent 配成"一键浇花装置"，按一下（run）就开跑
下集 docker-compose —— 把整套 OMA 服务配成"一键全家桶"，一条命令全开工

第 1 章

核心比喻：浇花装置

想象你在院子里装了一套自动浇花装置——这就是 deployment。

🚿 Deployment = 装好的浇花装置
里面配好了：浇什么花（agent）、用哪块地（environment）、水管接哪（resources）、几号水龙头（vault）、要不要定时（schedule）
▼ 按一下按钮
▶️ Run = 一次浇花
按按钮 → 装置照模板"复制"出一套实际浇水任务 → 开浇（= 生成一个会话去干活）
▼ 装置本体还在
🔁 Deployment 可以反复按，每次都是一次新 run
模板永不消耗，按一次复制一次 —— 这就是"部署"与"会话"的关系
🎯 一句话：deployment 是模板（配置 + 生命周期），run 是实例（按模板生成的真实任务）。 模板可以暂停（pause）、归档（archive）、反复使用 —— 每次 run 都是一次独立的会话。
第 2 章

三个概念，一张表分清

deployment 系统里其实有"三兄弟"。

📄
Deployment
一份运行配置模板：agent 快照 + 环境 + 资源 + 计划 + 状态。
ID：dep_xxx
生命周期：active / paused / archived
▶️
Run
按一次按钮的记录：谁按的（trigger）、啥时候、结果如何（成功 / 失败留 error）。
ID：drun_xxx
类型：manual（手动触发）
💬
Session（run 背后的真身）
run 本质上就是创建一套会话：session + thread + work 入队，交给环境执行。
ID：sess_xxx + thread_xxx + work_xxx

一次 run 一口气生成 4 个 ID（session / thread / work / run），像四联单一样成套开出。

第 3 章

API 地图：7 + 2 个入口

一个文件（handler.go，1921 行）挂了两个 router。

POST/v1/deployments创建部署（配装置）
GET/v1/deployments列表（分页 + 按 status/agent 过滤）
GET/v1/deployments/{id}查看详情
POST/v1/deployments/{id}更新配置（改了要重新预热技能）
POST/v1/deployments/{id}/archive归档（软删除，不能再 run）
POST/v1/deployments/{id}/pause暂停（带 reason，不能再 run）
POST/v1/deployments/{id}/unpause恢复
POST/v1/deployments/{id}/run⭐ 按按钮：触发一次运行
GET/v1/deployment_runs运行历史列表
GET/v1/deployment_runs/{id}单次运行详情

第 6 章

按按钮之后：run 的完整旅程

这是整个 deployment 系统的心脏 —— 模板变实例。

STEP 1 · 闸门
校验部署
存在？未归档？active？
➡️
STEP 2 · 验引用
validateRunReferences
agent / 环境 / vault / resources 现在还都在吗？有一个挂了 → 记一次失败的 run
➡️
STEP 3 · 开单
一次生成 4 个 ID
session + thread + work + run
➡️
STEP 4 · 装配
照模板复制
从 initial_events 生成会话事件
从 resources 解析会话资源
➡️
STEP 5 · 一个事务
四连写
Session + Thread + EnvironmentWork（queued）+ Run —— 全在一个事务里，要么全成要么全不成
➡️
STEP 6 · 广播
发 webhook 事件
session.created / pending / status_idled / thread_created ...
🧠 关键洞察：run 不执行任何 agent 逻辑 —— 它只负责把模板复制成一套会话， work 入队（queued），真正的活儿由 environments runner 消费执行。deployments 是编排壳，不是执行者。

第 8 章

一个有意思的细节：测试替身

create 和 run 里都有一行"魔法分支"。

如果 principal 是官方 SDK fixture 测试账号（isOfficialSDKFixturePrincipal）：

不碰数据库，直接返回写死的假数据（fixtureDeployment / fixtureDeploymentRun）。

作用：跑 Anthropic 官方 SDK 测试套件时，不需要真环境就能过 —— 这是"兼容层替身"，正式业务请求不经过它。

顺带：run 的引用校验失败也会记录一次失败的 run（不是直接 500 丢请求）—— 运行历史里有据可查。

下集 · docker-compose

另一个"deploy"：一键拉起全家桶

产品里的 deployment 是"一键浇花"；仓库根目录的 docker-compose.yml 是"一键开店"—— 一条命令把整个 OMA 服务全家开起来。

🏪 全家桶里有 7 个成员（docker-compose.yml）

🗄️postgres数据库（Postgres 17），存一切业务数据5432
⚡redis会话缓存（platform session store）6379
🪣minio对象存储（S3 兼容，存文件 + 技能包）9000/9001
🤖oma-server主 API 服务 —— 就是前面几站讲的单体进程38080
🏖️e2b-local沙箱网关 —— 用 host 网络管理宿主机 sandbox 容器3099
🌐caddyWeb 服务器：前端静态文件 + API 反代28080
📦init-web / init-envd一次性初始化容器（干完活就退，restart: no）—
下集 · 启动顺序

开店的讲究：谁先谁后不能乱

不是 7 个容器一起 up 就完事 —— 有依赖链。

STEP 1
init-web / init-envd
从镜像提取前端产物 + envd 二进制
➡️
STEP 2
postgres / redis / minio
基础设施先就绪（healthcheck 探活）
➡️
STEP 3
oma-server
依赖 3 个基础设施健康后才启动
➡️
STEP 4
e2b-local
等 init-envd 提取完（service_completed_successfully）
➡️
STEP 5
caddy
最后起：等 init-web 完成 + oma-server 健康

配套的健康检查体系：postgres 用 pg_isready、redis 用 redis-cli ping、minio 用 mc ready、oma-server 用 curl /healthz —— 等到的信号是"真的能干活"，不是"进程起来了"。

🧠 为什么 e2b-local 必须 host 网络？ 它要管理宿主机上的 sandbox 容器（挂载 docker.sock）， 必须和 Docker daemon 同网络。所以 compose 注释里写明：Docker Desktop（macOS/Windows）不支持，只有 Linux / OrbStack 能跑 —— 这是平台的硬约束。
下集 · 对照

两个 deploy 的对照表：别搞混

🚿
产品内 deployment
是什么：agent 的运行模板
哪来的：代码里 internal/deployments
操作：create / run / pause / archive
产物：run → session + thread + work
面向谁：API 用户（通过 SDK 调用）
🏪
docker-compose
是什么：整套服务编排
哪来的：仓库根目录 docker-compose.yml
操作：up / down / down -v
产物：7 个容器跑起来
面向谁：运维 / 部署者（docker CLI）
🎯 本质区别：产品 deployment 是 业务功能（给用户用的 API）， docker-compose 是 交付方式（把整个系统跑起来的手段）。一个在系统内部，一个在系统外面。

🎯 一句话记住本章

上集：deployment 是"agent 运行模板"，run 一次 = 复制出 session + thread + work 入队 + 广播 webhook；
下集：docker-compose 是"整套服务编排"，一条命令拉起 7 个容器，依赖链 + 健康检查保证顺序；
一个管 agent 怎么跑，一个管系统怎么起 —— 都是"一键"，但一个是产品功能，一个是运维工具。
