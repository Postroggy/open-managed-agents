OMA 内部参观 · 第 3 站

🧯 出错以后，全楼怎么反应

一个请求出错，它 不会静悄悄死掉，而是：
有人把错误说出来（error）· 有人决定客人看到什么（handler）· 有人兜底（中间件）

第 1 章

先看 Go 的总哲学：错误是值，不是异常

别的语言（Java/Python）出错会"扔"出去（异常），Go 不扔，它把错误当成一个普通的值，走完整个流程。

A
Java / Python：异常（throw）
错误发生时"扔"出去，程序一路往上弹，直到被 catch 接住。错误是流程的中断。 好处：不用每个函数都写检查；坏处：错误路径藏在控制流里，经常被忘记接。
B
Go：错误是返回值（error）
每个函数最后返回 (结果, error)，调用者必须亲手接住（不接编译期没强制，但代码规范强制）。 错误是流程的一部分，走完整个函数链。哲学：显式优于隐式 —— 错误路径和正常路径一样清晰可见，不搞魔法。
🎯 哲学一句话：异常是"出错就逃跑"，error 是"出错也上班"。 Go 让你无处可逃 —— 每层都得明明白白处理错误，这是 Go 刻意牺牲写码速度换来的可读性与可靠性。
第 2 章

一个错误在 OMA 里的一生（5 站）

以"上传文件超限"为例，跟着错误走一遍。

① 产生
db 报错
pgx 返回 pgx.ErrNoRows 或存储超限
➡️
② 翻译
db 包包装
errors.Is(err, pgx.ErrNoRows) → 转成自有哨兵 ErrNotFound / ErrStorageLimitExceeded（db 层不认识 HTTP）
➡️
③ 判断
handler 分类
errors.Is(err, db.ErrStorageLimitExceeded) → 决定：这是 403 还是 500？
➡️
④ 包裹
包装成 API 错误
httpapi.NewError(403, "permission_error", "Workspace storage limit exceeded")
➡️
⑤ 写出
JSON 响应
WriteError → {"type":"error","request_id":"req_...","error":{"type":"permission_error","message":"..."}}

每一站只做一件事：db 层只管"把错误说清楚"，handler 层只管"翻译成 HTTP 语义"，httpapi 只管"按 Anthropic 格式写出去"。

第 3 章

Go 的"错误三兄弟"：包装 的艺术

一个错误在链路里走，需要保留"我是什么 + 我在哪 + 原始细节"，Go 用三种姿势组合实现。

🚩
哨兵错误（sentinel）
包级别定义的"信号值"：var ErrNotFound = errors.New("not found")。
作用：跨层识别。db 层返回它，handler 层用 errors.Is 认出来 → 决定 404 还是 500。
为什么叫哨兵：像哨兵站岗，一看就知道"是这个错"。
🧅
包装（wrap）
fmt.Errorf("get file %q: %w", id, err)
作用：保留链路。往上抛时把"当时在干什么"拼进去，但用 %w 保住底层错误身份。
为什么重要：日志里你能看到"get file xxx: not found"——上下文和根因都在。而 %v 只保留字面量、丢身份（识别不了）——所以规范要求 wrap 必须用 %w。
🔎
判定（errors.Is / As）
errors.Is(err, db.ErrNotFound) / errors.As(err, &target)
作用：穿透包装链。不管包了几层 %w，Is 一路解开检查是不是同一个哨兵；As 把特定类型捞出来（比如 *http.MaxBytesError）。
为什么必须用它们：直接 err == db.ErrNotFound 在包装后永远 false —— 这是新手最常见的坑。
第 4 章

OMA 的双层错误模型：db 说人话，handler 定脸色

这是整个 OMA 后端设计边界的核心（CLAUDE.md 里明确写的规则）。

1
internal/db —— 只认错误，不认识 HTTP
db 层绝不构造 HTTP 状态码、绝不写 Anthropic 错误 JSON。它只返回： 普通 error（如 "storage limit exceeded"）、哨兵错误（ErrNotFound / ErrStorageLimitExceeded）、或结果状态。
依赖方向：db 不知道上面有谁，所以它永远能被测试、被复用、不会和某套 API 耦合。
2
handler / 资源层 —— 翻译官
handler 拿到 db 的错误，用 errors.Is 判断类型，然后在这里做映射： ErrStorageLimitExceeded → 403 permission_error；ErrNotFound → 404 not_found_error； 其它 → 500 api_error。错误响应用统一的 httpapi.WriteError，Anthropic 兼容格式。
💡 为什么要拆成两层？ 让 "是什么错"（事实） 和 "客人该看到什么"（表达） 分离。 db 只管事实，handler 管表达。这样换 API 协议（比如再开一个 gRPC 面）时，db 层一行都不用动。 这也是依赖方向规则：api 层可以依赖 db 层，db 层绝不反向依赖。
第 5 章

最后一道网：panic 兜底（recover）

Go 哲学是"错误都该显式返回"，但人总会犯错——panic 是"炸了"，不是"错了"。炸了谁来接？

恐慌发生
💥 某个 handler panic
比如空指针、数组越界、断言失败
➡️
中间件接住
🛡️ recoverMiddleware
defer func(){ recover() }() 在 panic 冒泡时接管（server.go:268）
➡️
记日志
📝 带上 request_id
log.Printf("panic request_id=%s: %v", ...) —— 事后能查是哪笔请求炸的
➡️
回 500
🤫 客人只见"内部错误"
绝不把堆栈抛给客户端 —— 那是信息泄露（能帮攻击者找漏洞）

关键区别：panic 是程序 bug（不该发生却发生）；error 是业务现实（必然发生：用户传错、数据库慢）。 OMA 不把 panic 当错误处理 —— 它只兜底、记日志、回 500，服务不崩溃、别的请求不受影响。

第 6 章

客人看到的脸色：错误码小抄

从 WriteError 出来的响应，永远是同一个形状：

📦 错误 JSON（Anthropic 兼容） httpapi/errors.go
{
  "type": "error",
  "request_id": "req_xxx",    // 串日志用的
  "error": {
    "type":    "permission_error",  // 机器可读
    "message": "Workspace storage limit exceeded"  // 人可读
  }
}
401authentication_error
钥匙缺失 / 无效 / 已停用 —— 你是谁？
403permission_error
身份有效但无权（组织不对、存储超限、工作区已归档）—— 你不行。
404not_found_error
资源不存在（故意不区分"存在但无权"）—— 查无此人。
400invalid_request_error
请求本身有毛病：缺字段、JSON 坏、缺 beta header。
413invalid_request_error
文件太大 / body 超限（MaxBytesReader 拦下的）。
500api_error
服务器内部错误 —— 细节藏起来，只留 request_id 让管理员查。

注意 404 的哲学：找不到 = 不存在（无论你有没有权限），避免给攻击者探路（"哦这个资源存在但我没权限"）。 这是 Anthropic 兼容 API 的标准语义，也是 OMA 的故意选择。

第 7 章

对照 Go 官方最佳实践：OMA 做对了什么，哪里偏了

用 Go 社区共识（Error handling 指南）给 OMA 打分。

最佳实践OMA 的做法评价
错误是值，显式返回 所有函数 (result, error)，handler 逐个 if err != nil 接住 ✅ 完全遵循
哨兵 + errors.Is/As，不比较字符串 ErrNotFound / ErrStorageLimitExceeded + errors.Is；errors.As(&http.MaxBytesError) 识别超限 ✅ 完全遵循
包装错误用 %w 保留链路 fmt.Errorf("put object %q: %w", ...) 普遍使用 ✅ 完全遵循
只处理错误一次（不重复打日志） 大部分场景：handler 顶部统一 log.Printf + 返回，干净 ✅ 遵循
panic 只用于不可恢复，recover 在边界 业务代码不 panic；recoverMiddleware 在 API 边界兜底 + 带 request_id 记日志 ✅ 遵循
db 层不泄露 HTTP 语义 db 返回哨兵/普通 error；handler 负责映射成 400/403/404/500 ✅ 遵循
错误类型携带结构化信息（建议型） 部分场景用哨兵判断分支，少数场景（如 413/403 需要分支）用 As 拿类型 ✅ 符合实际（哨兵方案在分层简单时足够）
每个错误都有用户可读文案（建议型） 有些内部错误 message 直接透传（如 err.Error() 拼进 400），对终端用户可能不够友好 ⚠️ 可优化：message 可能暴露内部细节（如 SQL 相关），建议统一"对外友好文案 + 内部细节进日志"
错误分类可扩展（大型项目可选） 靠散落的哨兵变量 + handler 里 if 判断，无集中注册表 ⚠️ 可优化：资源多了之后，容易漏分类导致 500 兜底；可考虑集中式错误映射
第 8 章

哲学：三句话 看懂整套机制

💬
显式优于隐式
错误是返回值，不是异常。每条出错路径都看得见，没人能在不看代码的情况下偷偷吞掉错误 —— Go 的哲学，OMA 严格执行。
🧱
事实与表达分离
db 只报"事实"（什么错了），handler 只定"脸色"（客人看到什么）。换协议不动数据层，换文案不动逻辑层 —— 依赖方向规则的副产品。
🛡️
边界兜底，细节保密
panic 在边界接住、带 request_id 记日志、客人只见"内部错误"。服务不崩、日志可查、敌人无料 —— 容错与安全的平衡点。

🎯 一句话记住本章

错误是值，不逃跑；哨兵认错，包装留痕；db 说事实，handler 定脸色；panic 兜底，客人只见 500。
