五岁小孩深度版 · 第 2 讲

OMA 后端架构
是怎么搭起来的？

一句话：一座一进门就发胸牌的餐厅——
每个人都带着身份卡在分工明确的厨房里干活。

第 1 章 · 总览

整个后端像一颗洋葱→

🧅 外层 · 门（中间件）
请求号 · 日志 · panic 兜底 —— 每个请求进门先过这三关
🗺️ 路由层
internal/api/server.go —— 每个 URL 指向哪个小厨房
👨‍🍳 资源层
internal/agents · sessions · files … —— Handler：验请求、调下层、回响应
📦 数据层
internal/db + internal/storage —— 只存取，不懂 HTTP

请求从外往里钻，数据从里往外流。每层只准跟相邻层说话。

第 2 章 · 请求旅程

一个请求进门后，走 6 站→

第 1 站
保安查票
提取 API key → 哈希 → 查库 → 验证身份
➜
第 2 站
发胸牌
把身份塞进 context → Principal
➜
第 3 站
看菜单
chi 路由：/v1/files → files.Handler
➜
第 4 站
小厨房
解析 multipart → 校验 → 算哈希
➜
第 5 站
两处存
内容进 MinIO，元数据进 PostgreSQL（同一事务）
➜
第 6 站
回话
Anthropic 兼容格式：type=error + request_id

第 2 站是整个架构的心脏。发完胸牌之后，所有小厨房都不需要再问"你是谁"——从 context 里掏胸牌就行。

每个小厨房里干活的步骤都一样：Principal → 校验 → 调 db/storage → 映射响应。

第 3 章 · 外层三兄弟

进门先过三关→

① 请求号中间件 —— 每个请求进门先发一个 req_xxx 号码。出事后靠它把散落各处的日志串成一条线。（server.go: requestIDMiddleware）

② 日志中间件 —— 进门前记一笔 >>> POST /v1/files，干完活再记一笔 <<< 200 12.3ms。还能识别客户端类型：SDK 来的 / curl 来的 / 控制台来的。（http_log.go: requestLoggingMiddleware）

③ panic 兜底中间件 —— 如果某个小厨房当场晕倒（panic），它接住，记下请求号，返回一个规范的 500，而不是让整个服务器崩溃。（server.go: recoverMiddleware）

这三兄弟是 Go 标准库 + chi 的"中间件"套路：一个函数包住下一个函数，像千层饼一样层层叠起来。

第 4 章 · 身份系统

两种客人，两种门票，一张胸牌→

🤖
SDK 客人
用 API key 进门的程序
Authorization: Bearer sk-ant-xxx
🧑‍💼
控制台客人
网页登录的用户（cookie session）
Cookie: sessionKey=xxx
🪪
Principal 胸牌
验证后统一发的身份卡
OrgID + WorkspaceID + APIKeyID + CredentialType…

API key 从不明文存库。只存它的 SHA-256 哈希。你每次出示门票，保安当场哈希，拿哈希去比对（db.go: GetAPIKey）。数据库被偷走也换不回钥匙。

胸牌是"多租户"的命根子。它装着 OrganizationID + WorkspaceID——之后每一次查库写库都带着这两个 ID，保证 A 公司永远看不到 B 公司的文件。这叫做显式多租户边界。

为什么是"显式"？因为数据库里可能有多条同名记录——比如两个组织各有一个叫 README.md 的文件。不带 scope 查就是越权事故。

第 5 章 · 分层

四层分工，箭头只准朝下→

internal/api
组装 + 路由 + 中间件
不写业务逻辑
⬇
资源包
agents / sessions / files…
handler + 业务编排 + 响应映射
⬇
internal/db · internal/storage
PostgreSQL 与 S3 的边界
纯数据访问
⬇
PostgreSQL · Redis · MinIO
记账本 / 便利贴 / 大仓库

铁律：internal/db 永远不能 import internal/api。DB 层不知道 HTTP 的存在——它不认识状态码，不认识 JSON 错误，只认识 Go 的错误（ErrNotFound、ErrDuplicate…）。

好处：换掉 HTTP 框架、换数据库、单独测试，都不牵连别的层。坏处（故意为之）：小厨房必须自己处理"DB 错误 → HTTP 错误"的翻译，代码会多一点。

第 6 章 · 实战解剖

拿 files 资源做一次"开胸手术"→

// ① Handler 自带一个小路由
router.Post("/", h.upload)
router.Get("/", h.list)
router.Get("/{file_id}", h.retrieve)
router.Delete("/{file_id}", h.delete)
// ② 整包先查 beta 头： anthropic-beta: files-api-2025-04-14
// ③ 上传：限大小 → 校验文件名 → 生成 ID → 流式上传到 S3
objectKey = "workspaces/{uuid}/files/{fileUUID}/{filename}"
// ④ 双写：MinIO 存内容 + PostgreSQL 存元数据（同一事务里做限额检查）
CreateFileIfWithinLimit(ctx, record, 限额) ← pg_advisory_xact_lock 防并发超限
// ⑤ 翻译错误：DB 的 ErrStorageLimitExceeded → HTTP 403 permission_error

看到没？请求处理真的是"翻译官"：把 HTTP 请求翻译成 DB 调用，再把 DB 的 Go error 翻译回 HTTP 错误。中间没有任何"全局状态"，全靠参数传来传去。

软删除：点删除，数据库里只把 deleted_at 打上时间戳（不是真删），同时去删 S3 对象；万一 S3 没删掉，就把任务丢给后台 cleanup worker 重试。删文件 = 记日志 + 发任务，两不误。

第 7 章 · 数据放哪

三个仓库各管什么→

📒
PostgreSQL 记账本
  • 一切元数据：文件、agent、session、key
  • 所有查询都带 WorkspaceID 过滤
  • 迁移用 goose（13 个版本文件）
  • 表不用外键——靠应用层保证完整
🏬
MinIO / S3 大仓库
  • 大件：文件内容、skill 包、批量结果
  • key 按 workspace 分目录：workspaces/{uuid}/files/…
  • 对象删除失败 → 进 cleanup job 队列

Redis 便利贴：控制台登录会话（platformsession），有 Save / Get / Delete 三个方法的小接口，默认 300 天过期。还有内存版实现，测试时不用起 Redis。

关键设计：存储后面藏着接口。ObjectStore 是个 interface（Put/Get/Delete/Bucket）。MinIO 只是其中一个实现——想换任何 S3 兼容存储，改一行配置就行。接口 = 把"怎么存"和"在哪存"解耦。

第 8 章 · 后台工人

不睡觉的后台工人→

🧹
cleanup worker
每 30 秒扫一遍 job 表，把没删干净的 S3 对象删掉（重试最多 10 次）
main.go: StartObjectCleanupWorker
📦
batch worker
处理异步消息批任务 + 过期清理
batches.StartBatchWorker
🏃
environments runner
跑 environment 的 runner 进程
environments.StartRunnerWithStore
⚡
skill prewarm
预加载 skill，减少首次调用延迟
skillprewarm.StartWorker
🪝
webhook worker
把事件投递给用户注册的 webhook 地址
webhooks.StartWorker

Worker 模式：数据库里的 jobs 表是"待办清单"。谁有空谁领单（租约），干完标记完成。多个 worker 也不怕抢单——有租约机制兜底。这是典型的异步任务队列套路。

第 9 章 · 设计规则

代码里到处写着"不许"→

🚫
没有外键
不用 PostgreSQL 外键约束；完整性靠应用层代码 + 迁移 + 测试守卫（tests/files_api_test.go 专门守着这条）。
🧬
三把 ID
每张核心表三件套：id（自增内部主键）、uuid（稳定业务标识）、external_id（对外 API 如 file_xxx）。各司其职。
🕰️
迁移只加不改
schema 变更永远新增 migration 文件（00013_xxx.sql），绝不改已应用的文件。老表改名也不删数据。
🔒
显式多租户
每条查询都带 organization_id / workspace_id，禁止只凭 external_id 全局查。
🧅
依赖只朝下
api → 资源包 → db / storage → 基础设施。谁都不能反向依赖。db 不认识 HTTP。
💬
对外说 Anthropic 的话
错误全部走 httpapi.WriteError，输出 type:error + request_id，让官方 SDK 读得懂。
第 10 章 · 学习地图

从哪读起→

1️⃣ 读 main.go — 大门：启动顺序一目了然（20 分钟）
2️⃣ 读 internal/api/server.go — 地图：路由/中间件/鉴权全在这（1 小时）
3️⃣ 读 internal/auth/auth.go — 胸牌长什么样（10 分钟）
4️⃣ 读 internal/httpapi/errors.go — 对外话术（5 分钟）
5️⃣ 读 internal/files/handler.go ⭐ — 完整闭环样本：请求→S3→DB→错误翻译（30 分钟）
6️⃣ 读 internal/db/files.go — 数据层长啥样：事务、限额、软删除（30 分钟）
7️⃣ 跳读 internal/sessions/ — 最复杂的资源：事件流、stream hub（进阶）
8️⃣ 看 internal/cleanup/worker.go — 后台工人样板（15 分钟）

心法：每读一个资源包，问自己三个问题——① 它怎么从 context 拿胸牌？② 它调了 db 的哪些方法？③ DB 错误是怎么翻译成 HTTP 错误的？这三个问题答完，你就真的读懂了。
