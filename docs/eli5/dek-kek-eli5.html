第二章 · 为什么包两层

直接用 KEK vs 信封加密

维度❌ 直接用 KEK 加密数据✅ 信封加密（DEK + KEK）
密钥数量1 个全局每行一个 DEK + 1 个 KEK
一行泄露所有数据全泄露 💥只泄露那一行 ✅
轮换 KEK重加密所有数据（巨慢）只重包 DEK（快 1000 倍）
KEK 暴露面频繁使用 = 暴露面大只碰"钥匙"不碰"数据" ✅
第三章 · 类比

用生活场景理解

🏠 你家的钥匙管理：

🔑 DEK = 每封信的信封（一次性，用完就扔）
🗝️ KEK = 你家主钥匙（只有一把，藏保险柜）

📮 邮局丢了一封信 → 只丢那封的钥匙 → 其他信全安全
🔐 主钥匙被偷 → 全部完蛋 → 所以 KEK 要藏最深

🏦 换主钥匙时 → 只需把每封信的钥匙重新包一层 → 信本身不用重写

第四章 · OMA 里怎么做

真实代码流程

① SealCredentialSecret（vaults/credential_secret.go）：
  · 明文 → Seal（生成新 DEK + 新 nonce → AES-GCM 加密 → KEK 包 DEK）
  · 立刻 清空明文（绝不留存！）
  · DB 只存信封

② credentialBinding：
  · 组织/工作区/vault/凭据 ID 组成 AAD（防"密文搬家"）

③ Open（读取时）：
  · 按 key_version 选 KEK → 解 DEK → 解数据 → 用完即清

第五章 · Insight

读完代码的深度理解

🎯 1. "每行一个 DEK"是安全粒度 —— 泄露半径 = 一行， AWS KMS 信封加密同款实践。

🔄 2. 轮换廉价所以敢轮换 —— 只重包 DEK，成本低， 系统才能频繁换主钥匙（合规要求）。

🔒 3. fail closed —— 未知 key_version 直接拒绝； 绑定不对解密失败：拿不准就拒绝。

🧹 4. 明文生命周期极短 —— 封口后立刻 clear， 开封后用完即清：内存里都不留。

🔌 5. 接口留扩展 —— KeyProvider 接口可接 KMS/Shamir， 信封格式不变（自研 → 可升级，不推翻）。
