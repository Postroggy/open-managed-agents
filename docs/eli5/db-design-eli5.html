第一章 · 三个名字

每张表都有三个名字

想象一张表是一个人 👤：他有 工号、身份证号、艺名。

ID类比用途为什么
id bigint 🏷️ 工号 数据库内部行身份（自增） 存储最便宜，但换库就变
uuid 🪪 身份证号 稳定业务标识 搬到哪里都不变（备份/搬迁/合并）
external_id 🎭 艺名 Anthropic 兼容 ID（file_xxx） 对外合同，不参与内部关联

💡 核心动机：可搬运性。
用户把数据导出、导入另一个实例（租户搬迁、跨库合并）——
工号会变，但 身份证号（uuid）永不变，引用不会断。

第二章 · 没有外键

为什么不用外键？（最反传统）

大多数数据库教你说"要用外键保护关系"。
OMA 说 不 —— 我用代码纪律换迁移自由。

✅ 用外键（传统）
🛡️数据库自己保证引用完整
🐢每次写入多一次锁校验
🧱改表结构要先拆外键再重建
🚫 不用外键（OMA）
⚡写入快，无锁开销
🔄42 个 migration 随意重建表
🧠完整性靠应用层三层防线

🧱 有外键时：改 schema 要先删外键 → 迁移 → 加回来（又慢又容易错）
⚡ OMA 没有外键：改表像拆乐高，migration 自由飞翔

第四章 · 三者闭环

三个决定如何互相成就

🔄 设计闭环
🚫
没有外键
schema 演进快，重建表无负担
📜
42 个 migration
每次变更留档，多环境一致
🪪
UUID 稳定引用
迁移时引用不断，跨库搬迁安全
▲ 相互成就 ▼
🎭
external_id 只做协议
内部关联全用 UUID，迁移范围可控
⚡
写入性能好
无外键锁开销，高并发不怕
🧠
代码纪律
三层防线替代数据库约束

🎯 一句话哲学：
给数据 全球身份证（UUID），对外留 艺名（external_id），
内部用 工号（bigint） —— 然后靠 migration + 代码纪律 而不是外键维护关系。
因为这是一个以「快速演进」和「可迁移」为第一优先级的系统。
