第一章 · 它是什么

Vault 凭据怎么加密？

vault 里存着敏感凭据（API key、token）。
不能明文存 —— secrets 用 信封加密 保护它们。

internal/secrets = 信封加密实现（4 个文件）：

🔑 provider.go —— KeyProvider 接口 + 本地实现（AES-256 KEK）
📜 kek.go —— KEK 加载/校验（base64 或文件）
✉️ service.go —— Seal/Open 封口/开封
🧪 测试 —— kek_test + secrets_test

第二章 · 信封加密是什么

双重加密结构

🎁
① 每个秘密一个 DEK（数据加密密钥）
随机的 32 字节一次性密钥 —— 用来加密真正的凭据
明文 → AES-GCM(DEK) → 密文
▼ 每个 DEK 再被 KEK 包裹
📦
② DEK 被 KEK（密钥加密密钥）包裹
系统只有一个 KEK（vault.master_key）—— 包裹所有 DEK
DEK → AES-GCM(KEK) → WrappedKey(含版本)
▼ 存进数据库
🗄️
③ 信封 = 密文 + 包裹的 DEK + 版本信息
DB 里只存信封，不存明文、不存 DEK
envelope = { ciphertext, wrapped_dek, key_version }
第三章 · 为什么双重加密？

信封加密的好处

🎯 1. 每行独立密钥 —— 一行数据一个 DEK：
一行的密钥泄露，只影响那一行，不影响全部。

🔄 2. 换 KEK 不用重加密数据 —— 只需解开 DEK 再重新包裹：
重加密的是"信封"不是"数据"（成本低 1000 倍）。

🏦 3. 密钥分层管理 —— 只有 KEK 是"顶级秘密"：
它放在 vault.master_key（base64 或文件），DEK 随数据走。

第四章 · KEK 旋转

换钥匙时旧数据还能打开

🔑 版本化 KEK：
current KEK (version N) + decrypt_only KEKs (version 1..N-1)

✉️ WrapDEK —— 只用当前 KEK 封口
🔓 UnwrapDEK —— 按信封记录的 key_version 选 KEK 开封

旋转流程：新 KEK 加入 current → 旧 KEK 降级为 decrypt_only →
旧信封仍能打开（版本匹配），新信封用新 KEK 封

第五章 · Service 层

Seal / Open

操作输入输出要点
SealBinding + 明文Envelope生成 DEK → 加密 → 包裹 DEK → 存版本
OpenBinding + Envelope明文按版本选 KEK → 解 DEK → 解数据
Binding绑定信息（scope）—— 参与 AAD 认证，防篡改
🔒 Binding 作为 AAD（附加认证数据）参与加密：如果 Binding 被改，解密直接失败 —— 防"把 A 的密文贴到 B 的上下文"。
第六章 · 文件分工

4 个文件

第七章 · Insight

读完代码的深度理解

🎯 1. "每行一个 DEK"是安全粒度 —— 一行泄露只影响一行， 这是云厂商的标准实践（AWS KMS 信封加密同款）。

🔄 2. 旋转成本极低 —— 换 KEK 只需重包 DEK（解+包）， 不用重加密数据 —— 所以系统敢频繁轮换。

🔒 3. fail closed 贯穿 —— 未知 KEK 版本直接拒绝； KEK 配置二选一（都配/都不配都报错）：拿不准就拒绝。

🔗 4. Binding 即 AAD —— 加密不只看密文，还绑定上下文： 防"密文搬家"攻击（替换攻击）。

🔌 5. 提供商可插拔 —— KeyProvider 接口让 KMS/Shamir 未来可接入， 不改信封格式、不改 DB 列 —— 接口隔离的价值。
